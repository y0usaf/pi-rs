# pi-coding-agent

Pi's coding agent ([`@earendil-works/pi-coding-agent`](https://github.com/earendil-works/pi)) as the `pi-rs` binary. It runs print mode (`pi-rs -p "..."`), the two headless modes (`--mode json`, `--mode rpc`) and a first port of the interactive mode on [pi-durable](../durable)'s harness and reads the same files as `pi`: settings, `auth.json`, `models.json`, AGENTS.md / CLAUDE.md, SYSTEM.md, APPEND_SYSTEM.md and skills.

Settings are upstream's own layer: the global `<agentDir>/settings.json` and the trusted project's `.pi/settings.json`, deep-merged with the project winning, every schema key with upstream's default, and setters that write back through a lock, replacing only the fields the session changed so keys this port does not know survive. pi-durable's auto-compaction follows them: `compaction.enabled`, `reserveTokens`, `keepRecentTokens` and the per-model overrides, with upstream's 16384 / 20000 when unset.

It won't: show settings screens, or the model and thinking selectors; run any slash command but `/quit`, `/new`, `/name`, `/session`, `/resume`, `/hotkeys`, `/compact`, `/tree`, `/fork`, `/clone`, `/export` and `/import`; answer RPC's `bash`, `abort_bash` and `export_html`, or its extension UI protocol; load themes; run a tool an extension registers, or the widgets, child agents and provider streams one adds; log in to any provider but Anthropic and OpenAI Codex; export a session as HTML.

The flags for what it won't do, `--export`, `--fork`, `--tui-mode` and `--verbose`, are refused before anything starts: `pi-rs: --export is not implemented yet`, exit 1. `--offline`, which would skip a model-catalog refresh this port never makes, is accepted and changes nothing; `--no-mcp` reads no `mcp.json`, `--no-themes` leaves only the built-in themes, `--no-extensions` keeps only the `--extension` paths and `--no-prompt-templates` only the `--prompt-template` paths, as upstream's do. A flag no option or extension defines is `Error: Unknown option: --foo`.

Its behaviour and `pi-ai`'s follow the upstream TypeScript at `bdb1517`; `pi-durable`'s follows `f1b2e77f` ([its README](../durable/README.md) says why the two pins differ). The parity scripts below compare the two on the same inputs.

## Try it

```sh
cargo run -p pi-coding-agent --bin pi-rs -- -p --model anthropic/claude-sonnet-4-5 "list the files here"
echo "summarize this" | cargo run -p pi-coding-agent --bin pi-rs -- @notes.md
```

Without `-p`, on a terminal, it opens the interactive mode (below). `--continue` (`-c`) goes on with the newest session for the working directory; `--session-id NAME` names a new session `NAME.db` and reopens it when it is there; `--no-session` keeps nothing.

`--list-models [search]` prints the models whose provider has auth, as `pi --list-models` does: provider, model, context, max-out, thinking and images, sorted by provider then model id, fuzzy-matched against the search pattern, then exits.

## Interactive mode

`cargo run -p pi-coding-agent --bin pi-rs` (or `pi-rs -c` to go on with the last session) opens a first port of upstream's interactive mode on pi-tui: the editor, the user's messages on their blue background, the assistant's reply streamed as Markdown, thinking in italics, one row per tool call (pending, green or red, with the built-in tools' previews and the bash timer), the working spinner and the two-line footer (cwd and git branch; tokens, cost, context use and model). Keys: Enter sends (while a reply runs it steers), Escape aborts the reply, Ctrl+C clears the editor and twice quits, Ctrl+D quits on an empty editor, Ctrl+O expands tool output. A line starting `!` runs a bash command in the editor's cwd with the shell `shellPath` and `shellCommandPrefix` name and streams its output into the bordered block upstream draws: the command, the output as the model's copy of it is cut, `(exit N)` or `(cancelled)`, and the truncation warning with the full output's path. Escape kills the command, the editor's border is green while the line starts with `!`, and a `!` line sent while one runs answers upstream's warning. The run is stored as upstream's `bashExecution` message, which the next request carries as `Ran` and the command in backticks with the output fenced; `!!` draws the same block in the dim colour and keeps the run out of that context. A message queued during a reply shows above the status line as `Steering:` (Enter) or `Follow-up:` (Alt+Enter, which waits for the reply to finish), and Alt+Up puts them all back in the editor, as Escape does before it aborts the reply. `<agentDir>/keybindings.json` rebinds them by id, as upstream's does: `{"app.interrupt": "ctrl+k"}`, with the legacy names still read and a value the schema rejects ignored. Typing `/` lists the builtin commands and `@` completes file paths through `fd`. `/quit`, `/new` (a new session file in the same folder), `/name [text]`, `/session`, `/resume` (the session picker), `/hotkeys`, `/compact [instructions]`, `/tree`, `/fork`, `/clone`, `/export <path>.jsonl`, `/import <path.jsonl>`, `/login` and `/logout` work; every other builtin answers that it is not available in pi-rs yet, and an unknown `/x` goes to the model as a message, as upstream does. The screen is built from pi-durable's agent events (`Conversation::events`), so a session killed mid-reply (even `kill -9`) reopens with `-c` showing what was stored, and the harness resumes the unfinished turn. Colors are upstream's dark theme by default, truecolor when `COLORTERM` says so.

Code in fenced blocks is highlighted by a tokenizer of this port's own, not highlight.js: it knows comments, strings, numbers, keywords, function calls and capitalized type names for rust, javascript, typescript, python, bash, go, c, c++, java, kotlin, ruby, lua, sql, css, json, yaml and toml, and colors them with the theme's `syntax*` tokens through upstream's own cli-highlight mapping. A fence in any other language stays `mdCodeBlock`, as upstream draws a language it does not know; where a language is recognized, fewer tokens carry a color than highlight.js gives them.

The startup header follows `quietStartup`: `true` hides it, `"header"` keeps the logo and key hints and drops the details line, and `false` shows both. `treeFilterMode` picks the filter `/tree` opens with.

`/tree` is upstream's session tree (its filter keys, search, folding and branch markers): picking an entry moves the session's leaf there, which pi-durable spells as a forked conversation, and a picked user message reopens in the editor. Two things the tree shows upstream are missing: entry labels (and the label keys and timestamps that go with them) and branch summaries, so picking an entry never asks whether to summarize the branch.

`/fork` lists the session's user messages and `/clone` takes the current leaf; both write a new session file holding the active path up to that point and switch the screen to it, as upstream's branch files do, and `/fork` puts the picked message back in the editor. Each says so in the transcript and names the file it wrote, where upstream says "Forked to new session" or "Cloned to new session" on the status line.

Themes are upstream's own JSON files: `dark` and `light` are built in, and custom themes load from `<agentDir>/themes`, the trusted project's `.pi/themes` and the paths the `themes` setting or `--theme` names, each theme's `vars` and okhsl, oklch, hex or palette-index colors read as upstream reads them. The `theme` setting picks one, and a pair like `light/dark` picks the first theme on a light terminal and the second on a dark one, as `COLORFGBG` reports it. The default, `system`, is the built-in theme of the terminal's appearance; upstream generates one from the colors the terminal answers a query with, which this port never asks for. `--use-theme NAME` starts with that theme in place of the setting's. A theme file that does not load says why and falls back to the system theme. In `/settings`, the theme row lists every theme, highlighting one draws the screen with it, and picking one saves it; its `automatic` row picks a theme for each terminal appearance and saves them as the pair.

`/login` configures a provider and `/logout` removes the credential it saved: without an argument `/login` asks whether to sign in with an account or with an API key and then lists the providers, where `/login <provider>` starts the one whose id or name matches. Accounts sign in through upstream's OAuth flows, Anthropic with a loopback callback or a pasted copy-code, OpenAI Codex with a loopback callback or a device code, xAI with a device code; the dialog shows the URL, the device code and every question the flow asks, Escape cancels, and the credential lands in the same `auth.json` with the same lock and shape as `pi`, so both read it and either refreshes the token. Only Anthropic and OpenAI Codex accounts and the Anthropic API key are offered, and an OAuth endpoint can be pointed elsewhere with `PI_OAUTH_<PROVIDER>_<FIELD>`, as in `PI_OAUTH_ANTHROPIC_TOKEN_URL`, which the login check uses. Every flow polls a device code through one loop with upstream's `device-code.ts` behind it: the five-second default interval, `slow_down` raising it, the expiry deadline and its three messages.

Not there yet: `/share`, `/bug`, `/copy`, `/changelog` and `/reload`, the other providers' logins, image display, reloading a theme file as it changes, and the editor's embedded status. A `!` command run while a reply streams writes its block into the transcript at once, where upstream keeps it above the editor until the reply ends. A message typed while a compaction runs is sent as a prompt rather than queued for after it. The settings' enable and disable lists for skills and prompts are not read either: a file in the default directories always loads. A resumed session from another folder keeps the current folder, where upstream switches to the session's own; `/resume` reports in the transcript, where upstream uses the status line.

## Codemode

`codemode` lets the model write JavaScript that calls other tools: `--tools +codemode`, or `+codemode` in `defaultTools`. A script is an async function body (`await` and `return` work) in a QuickJS VM inside a hidden child of the `pi-rs` binary, one script per child and at most `PI_CODEMODE_MAX_WORKERS` (2) at a time; the deadline or an abort kills the child, so a `while (true) {}` cannot outlive it and no child is left behind. Scripts see `tools.<name>(args)`, `ALL_TOOLS`, `text()`, `image()`, `console.*`, `exit()`, `store()`/`load()` and `return`, and nothing else: no Node, timers, network or filesystem. A `// @options:` first line sets `max_output_tokens` and `timeout_ms`, and a script with no deadline runs until it ends.

`codemode.mode` decides how the tools are presented, as upstream's `prepareLoadout` does. `on`, the default, keeps the direct tools declared and appends to each one's description how a script calls it ("Codemode: `tools.read(args)` resolves to a string."); the codemode description lists only the tools that are not declared. `only` declares codemode alone, leaves the active direct tools' declarations out of the request as hidden declarations while they stay callable from a script, and lists every one of them in the codemode description under a `### <name>` heading with its TypeScript declaration in a `declare const tools` block, so `defaultTools: ["+codemode"]` with `"mode": "only"` sends exactly one tool. `codemode.inlineBudget` (3000 tokens by default) bounds the declarations: tools that do not fit are left out of the description, cheapest first. A tool's exposure decides where it appears: `direct` (declared, callable while active), `model-only` (codemode itself), `codemode` and `deferred` (callable from a script, never declared, the latter not listed either) and `hidden` (never declared), which is what MCP tools will use.

A nested call runs through the same validation, before/after tool hooks and permission gates as a model-issued one, and reaches the agent's tools without being declared to the model. Only the script's output reaches it: text items are numbered (`==> text 1/2 <==`) when there are several, `console.*` lines follow in one `<console_output>` block, the whole output is truncated to `max_output_tokens` (10000 by default) with the full text spilled to a temp file, and an image from `image()` is saved to a temp file whose path the result names. The result's details carry the nested calls and their durations. A script's `store()` writes become one `codemode-store` entry after its result, and `load()` reads the entries on the current branch from the root, so a value written in an earlier run is still there and `/tree` back to before it brings the older value back.

## Headless modes

`--mode json` is print mode with the session's events as one JSON object per line on stdout instead of the final text, so a client sees the assistant's text as it streams: `pi-rs --mode json -p "list the files here"`. `--mode rpc` takes the same commands upstream's RPC mode does as JSON lines on stdin, and answers them on that one stdout stream beside the events, so a client reads the reply and the stream it caused in order. Every command upstream carries is answered but `export_html` and the extension UI protocol, which say `pi-rs: <command> is not implemented in RPC mode`; a type no mode has says `Unknown command: <type>`. Slash text in a `prompt` is a prompt, since no extension or template here claims the name, as upstream's RPC mode does. A `bash` command runs on its own thread while the loop keeps reading, so its output arrives as `bash_execution_update` lines and `abort_bash` stops it mid-command; the run joins the context as upstream's `bashExecution` message, and the command answers with upstream's `BashResult` (`output`, `exitCode`, `cancelled`, `truncated`, `fullOutputPath`).

`new_session`, `switch_session`, `fork` and `clone` write or open the session file they name and switch the run to it, as the interactive commands do, and `get_tree`, `get_fork_messages`, `get_session_stats`, `get_entries` and `clear_queue` read pi-durable's entries, usage and inbox. `fork` takes the entry ids `get_entries` and `get_fork_messages` report, which are numbers here rather than upstream's short strings, and a branched session replays its entries into a new file, so its ids and its recorded usage differ from the session it came from. `set_steering_mode`, `set_follow_up_mode`, `set_auto_compaction` and `set_auto_retry` are saved to settings and reported by `get_state`, but the run in flight keeps the modes it opened with, which pi-durable fixes while the harness is open.

## Sessions

Each run is one pi-durable conversation in a SQLite file, `<agentDir>/sessions/--<cwd>--/<uuidv7>.db` (or under `--session-dir`, `$PI_CODING_AGENT_SESSION_DIR`, or the `sessionDir` setting). `--session FILE` opens that file, `--session-id NAME` writes to `NAME.db` next to it, `--continue` reopens the newest branch, and `--resume` picks from the sessions in this folder or in all of them. A branch of the tree is another conversation in the same file, forked at the entry the session moved to. `--fork <path|id>` copies a session into a new file under a new id, refusing one whose run is still in flight, and leaves the source untouched. These are not upstream's JSONL session files and `pi` cannot open them; `/export` writes one it can. A session's display name and the session it was forked from are one session-scope document (`pi.session-info`) inside the file, so a copy of the file carries them.

`/export PATH.jsonl` writes the conversation's current branch in upstream's session format (`core/session-export.ts`): the `type: "session"` header, then the branch's entries with `parentId` re-chained, one JSON object per line. `pi --export` reads what it writes. Upstream records each model and thinking change as an entry; pi-durable keeps both in the conversation's agent document, so the file carries the current pair once, at the head, where upstream writes them for a new session. Entry timestamps are the export's, since pi-durable stores no entry times, and a `compaction` entry carries `tokensBefore: 0`. A `pi.reset` entry, which marks where a run's context was reset, has no upstream type and is dropped. A path that ends in anything but `.jsonl`, or no path at all, is upstream's HTML export, which is not ported, so `/export` refuses it. The system-prompt entry carries pi-rs's own prompt, whose tools declare no `constrainedSampling` and whose docs path is pi-rs's, so an export of a session pi-rs wrote differs from `pi`'s only there; a session imported from a `pi` file keeps upstream's prompt and exports identically.

`/import PATH.jsonl` reads an upstream session file into a new `.db` in the session directory, named after the file's session id, with the token totals its messages carry and the file's model, thinking level and cwd set on the conversation. It asks `Import session` / `Replace current session with <path>?` first, as upstream's confirm dialog does, and `Import cancelled` when the answer is no. The loop then switches to that file, as upstream's import does: the session's model, thinking level and cwd become the file's, and the chat redraws from its transcript, so `/session` reports it without a restart. A file whose cwd no longer exists is refused, naming both paths as upstream does, though upstream then offers to use the current directory and this does not. Entry types with no durable place are dropped — `label`, `custom`, `custom_message`, `branch_summary`, `usage` and `session_info` (the session's name) — a `model_change` or `thinking_level_change` becomes the conversation's model or thinking level instead of an entry, and a `context_edit` whose target is in the file is kept. The JSONL files `pi` keeps are then readable here, and a session this writes back out is the file upstream wrote, apart from ids and timestamps.

## MCP servers

Servers come from `<agentDir>/mcp.json` and, in a trusted project, from `<cwd>/.pi/mcp.json`, both in the `mcpServers` shape other MCP clients use: a `command` starts a stdio server, a `url` reaches a streamable HTTP one, and a project entry replaces a global one of the same name, or overrides its `enabled`, `exposure` and `toolExposure` when it sets nothing else. They connect before the first turn, which waits at most ten seconds for them, and their tools are the agent's own, named `mcp__<server>__<tool>` (with a `sha256` suffix when a name is too long or two tools sanitize to one name): the server's `inputSchema` becomes the tool's parameters, and a result's content blocks become text and images, with text over 20KB cut in the middle and the whole output in a temp file. `--no-mcp` reads no `mcp.json` at all.

A server's tools are declared to the model only with `"exposure": "direct"`, or a `toolExposure` entry that says so. The default, `codemode`, and `deferred` are not ported, since this port has neither the codemode tool nor `tool_search`: such a server is listed in the `mcp_servers` system prompt section with its description, its tools cannot be called, and the interactive mode says so once at startup. An HTTP server that answers 401 fails, because OAuth sign-in is not ported, and `"auth": { "provider" }` is accepted by the config validation but sends no token. The interactive mode reports the servers that failed to connect and the config errors in the transcript at startup; print mode, like upstream's, has no UI to report them in. A connection that drops is not re-established, so that server's tools fail until the next run.

## Extensions

`packages` (a package directory, a store path for an npm package), the `extensions` setting, `--extension` and the `<cwd>/.pi/extensions` and `<agentDir>/extensions` directories name what to load, and the child finds inside them what upstream's resource loader finds: one level deep, by `package.json`'s `pi.extensions`, `index.ts` or `index.js`. One Node child per session imports each entry point with Node's own type stripping and calls the factory; it comes from the `extension-host` directory installed beside the binary, and `PI_EXTENSION_HOST` names another copy.

A command a factory registers is listed where upstream lists it — `/` autocomplete and RPC `get_commands`, as `"source": "extension"` with the entry point's path; upstream tags the autocomplete entry with where the extension came from (`[u]` for the agent directory) and pi-rs does not. Typing one runs the command's handler with the text after its name, in place of sending the prompt, as upstream does. The child answers `@earendil-works/pi-coding-agent`, `@earendil-works/pi-ai` and `@earendil-works/pi-tui` with a stub, so a package that imports from them loads: `getAgentDir()` answers with the agent directory, and every other member records itself the first time a package uses it, which the session then reports as `Warning: <path> uses registerTool, which pi-rs does not implement yet`.

A package that fails to load is reported as upstream reports it, `Warning: Failed to load extension: <message>`, and the session goes on; with nothing configured no child starts and nothing changes.

The events upstream hands extensions reach them through the harness. `session_start`, `session_shutdown` (reason `quit` only), `agent_start`, `agent_end`, `agent_settled` once the queue is empty, `message_start` at the first streamed chunk, `message_update` for every streamed version of a message, `message_end`, and `input` before a prompt is sent. An answer changes what is stored: a `message_end` handler that returns a message of the same role replaces the message before it is committed — on the abort path too — so a resumed session reads the replacement, and an `input` handler's `transform` is what the model sees. `ctx.abort()` stops the run the way Escape does, `ctx.ui.notify` shows a notice, and `sendUserMessage` with `deliverAs: "followUp"` queues a turn after this one.

Each handler has ten seconds before the child is taken for wedged and the event dropped, so an extension that hangs cannot hang the TUI. Three shapes differ from upstream: `message_start` carries the first streamed chunk rather than an empty message, `message_end` answers only for assistant messages and `input` only for a prompt that is one text block, and `agent_end` and `agent_settled` carry no `messages`.

## What matches upstream, and how it is checked

`parity/run.sh` (with `PI_TS` pointing at an upstream checkout with `node_modules` installed, and the models catalog hydrated) runs each check against the TypeScript and against this crate:

- tools (`tools.json`): `read`, `write`, `edit`, `bash`, `grep`, `find` and `ls` on the same files, compared on the exact text, details and error messages they return;
- model resolution (`models.json`): `--model`, `--provider`, `:thinking` suffixes, `--models` scopes and their warnings;
- the system prompt (`prompt.json`): the tools list and rules, context files up the directory tree (with worktree shadowing), SYSTEM.md and APPEND_SYSTEM.md with project trust, `--system-prompt` and `--append-system-prompt`, and skills discovery with frontmatter, ignore files and name collisions;
- print mode end to end (`e2e.json`): `pi -p` and `pi-rs -p` against one scripted OpenAI-compatible server, compared on every request they send (system prompt, tool declarations, messages, tool results) and on stdout, stderr and the exit code;
- the modes end to end (`examples/modes_e2e.rs`, run by `nix flake check`): the `--mode json` events of a run, a prompt template from the agent directory expanding in a print-mode prompt, and `--mode rpc` answering commands and switching, forking and cloning a session;
- the codemode sandbox (`checks.codemode-e2e`): the hidden child's messages, a script calling a tool, the typo guard, a script waiting on nothing, the deadline, an abort, the memory limit, `store()` writes and a value stored in one run and loaded in the next, `@options` parsing, and a `pi-rs -p` run whose model calls `codemode` with a script that calls `read`.

`nix flake check`'s `extensions-e2e` writes an extension of its own and drives the built binary with it: `packages` names it, a command appears in RPC `get_commands` with the schema the package computed at load, `--extension` adds a second, `--no-extensions` keeps only that one, a package that throws and one that registers a tool are reported and leave nothing behind, and an empty settings file starts no child. In a print-mode run against a fake model it checks that every event arrives, that a `message_end` replacement is what the next request holds in place of the reply, that an `input` transform is what the model was asked, and that a command runs with its arguments.

## Where it differs

- HTTP errors from OpenAI-compatible servers print the whole JSON body (a pi-ai difference, listed in `crates/ai/parity/known.json`), and openai-completions tool declarations carry `strict: false`.
- A `// @options:` line holding invalid JSON reports the JSON parser's own message, which reads differently from V8's.
- A script's nested calls run one at a time, where upstream runs a script's concurrent calls in parallel, because pi-durable's harness is synchronous: a tool call cannot run beside another.
- The codemode tool's description lists no `searchTools`, `describeTool`, `describeNamespace` or `models` namespace, which are not ported, and the prelude's typo hint still mentions `searchTools`.
- A codemode row shows its nested calls when the script ends, not as they run. A codemode call a crash interrupts is reported as `Tool codemode was interrupted and may have partially run`, where upstream replays the script and hands it the nested results it already had: pi-rs keeps no nested-call journal, so a replay would run those tools a second time.
- `/tree` lists a `codemode-store` entry as `[codemode-store]`, where upstream's generic custom-entry row reads `[custom: codemode-store]`.
- A nested call resolves to the tool's text: no pi-rs tool declares structured output, so `tools.bash(...)` resolves to a string where upstream's resolves to an object with `exit_code`, `output` and the rest, and the description says `Promise<string>`.
- The codemode description groups tools by namespace upstream; pi-rs has no namespaces yet, so every tool is listed under one `Nested tools:` heading.
- Skill frontmatter is read by a small YAML reader covering what skills use (plain, quoted and block scalars, booleans); other YAML in a skill file is skipped rather than rejected.
- The docs paths in the system prompt name `$PI_PACKAGE_DIR`, or the directory of the `pi-rs` binary, since there is no npm package.
- `fd` and `rg` are used from the agent's bin directory or `PATH`; they are not downloaded.
- `--mode json` writes no `session` header line, because the header upstream writes describes its JSONL session file and these sessions are SQLite. It also carries pi-durable's own events beside upstream's (`agent_changed`, `submission`, `usage_changed`, `inbox_update`, `deferred_poll`), and fewer `message_update` lines: the harness folds a message's first and last commit into its `message_start` and `message_end`, so `text_start`, `text_end` and a tool call's `toolcall_start` / `toolcall_delta` / `toolcall_end` arrive only when the block lands mid-message, and `tool_execution_update` only for a tool that reports partial output, which no built-in does.
- Assistant messages in that stream carry pi-ai's fields: `durationMs` and `responseId`, no `thinkingLevel`, and a tool call with no `partialArgs` or `streamIndex`; `toolsAdded` carries no `constrainedSampling`, and a tool call's `structuredContent` is the tool's own details object.
- `--list-models` prints the auth each provider has and the catalog pi-ai ships, so its rows for a model match `pi --list-models`'s only while both binaries carry the same catalog: a different `pi` version can list another context window, or a model this crate lacks.
