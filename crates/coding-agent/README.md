# pi-coding-agent

Pi's coding agent ([`@earendil-works/pi-coding-agent`](https://github.com/earendil-works/pi)) as the `pi-rs` binary. It runs print mode (`pi-rs -p "..."`), the two headless modes (`--mode json`, `--mode rpc`) and a first port of the interactive mode on [pi-durable](../durable)'s harness and reads the same files as `pi`: settings, `auth.json`, `models.json`, AGENTS.md / CLAUDE.md, SYSTEM.md, APPEND_SYSTEM.md and skills.

Settings are upstream's own layer: the global `<agentDir>/settings.json` and the trusted project's `.pi/settings.json`, deep-merged with the project winning, every schema key with upstream's default, and setters that write back through a lock, replacing only the fields the session changed so keys this port does not know survive. pi-durable's auto-compaction follows them: `compaction.enabled`, `reserveTokens`, `keepRecentTokens` and the per-model overrides, with upstream's 16384 / 20000 when unset.

It won't: show settings screens, or the model and thinking selectors; run any slash command but `/quit`, `/new`, `/name`, `/session`, `/resume`, `/hotkeys`, `/compact`, `/tree`, `/fork`, `/clone`, `/export` and `/import`; answer RPC's `bash`, `abort_bash` and `export_html`, or its extension UI protocol; load extensions, prompt templates or themes; log in (it reads the credentials `pi` stores, and refreshes Anthropic and OpenAI Codex OAuth tokens); export a session as HTML.

The flags for what it won't do, `--export`, `--fork`, `--extension`, `--prompt-template`, `--theme`, `--use-theme`, `--tui-mode` and `--verbose`, are refused before anything starts: `pi-rs: --export is not implemented yet`, exit 1. The flags that turn a resource off — `--no-extensions`, `--no-themes`, `--no-prompt-templates` — and `--offline`, which would skip a model-catalog refresh this port never makes, are accepted and change nothing; `--no-mcp` reads no `mcp.json`. A flag no option or extension defines is `Error: Unknown option: --foo`.

Its behaviour and `pi-ai`'s follow the upstream TypeScript at `bdb1517`; `pi-durable`'s follows `f1b2e77f` ([its README](../durable/README.md)). The parity scripts below compare the two on the same inputs.

## Try it

```sh
cargo run -p pi-coding-agent --bin pi-rs -- -p --model anthropic/claude-sonnet-4-5 "list the files here"
echo "summarize this" | cargo run -p pi-coding-agent --bin pi-rs -- @notes.md
```

Without `-p`, on a terminal, it opens the interactive mode (below). `--continue` (`-c`) goes on with the newest session for the working directory; `--session-id NAME` names a new session `NAME.db` and reopens it when it is there; `--no-session` keeps nothing.

`--list-models [search]` prints the models whose provider has auth, as `pi --list-models` does: provider, model, context, max-out, thinking and images, sorted by provider then model id, fuzzy-matched against the search pattern, then exits.

## Interactive mode

`cargo run -p pi-coding-agent --bin pi-rs` (or `pi-rs -c` to go on with the last session) opens a first port of upstream's interactive mode on pi-tui: the editor, the user's messages on their blue background, the assistant's reply streamed as Markdown, thinking in italics, one row per tool call (pending, green or red, with the built-in tools' previews and the bash timer), the working spinner and the two-line footer (cwd and git branch; tokens, cost, context use and model). Keys: Enter sends (while a reply runs it steers), Escape aborts the reply, Ctrl+C clears the editor and twice quits, Ctrl+D quits on an empty editor, Ctrl+O expands tool output. Typing `/` lists the builtin commands and `@` completes file paths through `fd`. `/quit`, `/new` (a new session file in the same folder), `/name [text]`, `/session`, `/resume` (the session picker), `/hotkeys`, `/compact [instructions]`, `/tree`, `/fork`, `/clone`, `/export <path>.jsonl` and `/import <path.jsonl>` work; every other builtin answers that it is not available in pi-rs yet, and an unknown `/x` goes to the model as a message, as upstream does. The screen is built from pi-durable's agent events (`Conversation::events`), so a session killed mid-reply (even `kill -9`) reopens with `-c` showing what was stored, and the harness resumes the unfinished turn. Colors are upstream's dark theme, truecolor when `COLORTERM` says so.

`/tree` is upstream's session tree (its filter keys, search, folding and branch markers): picking an entry moves the session's leaf there, which pi-durable spells as a forked conversation, and a picked user message reopens in the editor. Two things the tree shows upstream are missing: entry labels (and the label keys and timestamps that go with them) and branch summaries, so picking an entry never asks whether to summarize the branch.

`/fork` lists the session's user messages and `/clone` takes the current leaf; both write a new session file holding the active path up to that point and switch the screen to it, as upstream's branch files do, and `/fork` puts the picked message back in the editor. Each says so in the transcript and names the file it wrote, where upstream says "Forked to new session" or "Cloned to new session" on the status line.

Not there yet: `/share`, `/bug`, `/copy`, `/changelog`, `/login`, `/logout` and `/reload`, `!` bash, image display, syntax highlighting in code blocks, the light theme, the editor's embedded status, and upstream's keybinding configuration. A resumed session from another folder keeps the current folder, where upstream switches to the session's own; `/resume` reports in the transcript, where upstream uses the status line.

## Headless modes

`--mode json` is print mode with the session's events as one JSON object per line on stdout instead of the final text, so a client sees the assistant's text as it streams: `pi-rs --mode json -p "list the files here"`. `--mode rpc` takes the same commands upstream's RPC mode does as JSON lines on stdin, and answers them on that one stdout stream beside the events, so a client reads the reply and the stream it caused in order. Every command upstream carries is answered but `bash`, `abort_bash`, `export_html` and the extension UI protocol, which say `pi-rs: <command> is not implemented in RPC mode`; a type no mode has says `Unknown command: <type>`. Slash text in a `prompt` is a prompt, since no extension or template here claims the name, as upstream's RPC mode does.

`new_session`, `switch_session`, `fork` and `clone` write or open the session file they name and switch the run to it, as the interactive commands do, and `get_tree`, `get_fork_messages`, `get_session_stats`, `get_entries` and `clear_queue` read pi-durable's entries, usage and inbox. `fork` takes the entry ids `get_entries` and `get_fork_messages` report, which are numbers here rather than upstream's short strings, and a branched session replays its entries into a new file, so its ids and its recorded usage differ from the session it came from. `set_steering_mode`, `set_follow_up_mode`, `set_auto_compaction` and `set_auto_retry` are saved to settings and reported by `get_state`, but the run in flight keeps the modes it opened with, which pi-durable fixes while the harness is open.

## Sessions

Each run is one pi-durable conversation in a SQLite file, `<agentDir>/sessions/--<cwd>--/<uuidv7>.db` (or under `--session-dir`, `$PI_CODING_AGENT_SESSION_DIR`, or the `sessionDir` setting). `--session FILE` opens that file, `--session-id NAME` writes to `NAME.db` next to it, `--continue` reopens the newest branch, and `--resume` picks from the sessions in this folder or in all of them. A branch of the tree is another conversation in the same file, forked at the entry the session moved to. `--fork <path|id>` copies a session into a new file under a new id, refusing one whose run is still in flight, and leaves the source untouched. These are not upstream's JSONL session files and `pi` cannot open them; `/export` writes one it can. A session's display name and the session it was forked from are one session-scope document (`pi.session-info`) inside the file, so a copy of the file carries them.

`/export PATH.jsonl` writes the conversation's current branch in upstream's session format (`core/session-export.ts`): the `type: "session"` header, then the branch's entries with `parentId` re-chained, one JSON object per line. `pi --export` reads what it writes. Upstream records each model and thinking change as an entry; pi-durable keeps both in the conversation's agent document, so the file carries the current pair once, at the head, where upstream writes them for a new session. Entry timestamps are the export's, since pi-durable stores no entry times, and a `compaction` entry carries `tokensBefore: 0`. A `pi.reset` entry, which marks where a run's context was reset, has no upstream type and is dropped. A path that ends in anything but `.jsonl`, or no path at all, is upstream's HTML export, which is not ported, so `/export` refuses it. The system-prompt entry carries pi-rs's own prompt, whose tools declare no `constrainedSampling` and whose docs path is pi-rs's, so an export of a session pi-rs wrote differs from `pi`'s only there; a session imported from a `pi` file keeps upstream's prompt and exports identically.

`/import PATH.jsonl` reads an upstream session file into a new `.db` in the session directory, named after the file's session id, with the token totals its messages carry and the file's model, thinking level and cwd set on the conversation. It asks `Import session` / `Replace current session with <path>?` first, as upstream's confirm dialog does, and `Import cancelled` when the answer is no. The loop then switches to that file, as upstream's import does: the session's model, thinking level and cwd become the file's, and the chat redraws from its transcript, so `/session` reports it without a restart. A file whose cwd no longer exists is refused, naming both paths as upstream does, though upstream then offers to use the current directory and this does not. Entry types with no durable place are dropped — `label`, `custom`, `custom_message`, `branch_summary`, `usage` and `session_info` (the session's name) — a `model_change` or `thinking_level_change` becomes the conversation's model or thinking level instead of an entry, and a `context_edit` whose target is in the file is kept. The JSONL files `pi` keeps are then readable here, and a session this writes back out is the file upstream wrote, apart from ids and timestamps.

## MCP servers

Servers come from `<agentDir>/mcp.json` and, in a trusted project, from `<cwd>/.pi/mcp.json`, both in the `mcpServers` shape other MCP clients use: a `command` starts a stdio server, a `url` reaches a streamable HTTP one, and a project entry replaces a global one of the same name, or overrides its `enabled`, `exposure` and `toolExposure` when it sets nothing else. They connect before the first turn, which waits at most ten seconds for them, and their tools are the agent's own, named `mcp__<server>__<tool>` (with a `sha256` suffix when a name is too long or two tools sanitize to one name): the server's `inputSchema` becomes the tool's parameters, and a result's content blocks become text and images, with text over 20KB cut in the middle and the whole output in a temp file. `--no-mcp` reads no `mcp.json` at all.

A server's tools are declared to the model only with `"exposure": "direct"`, or a `toolExposure` entry that says so. The default, `codemode`, and `deferred` are not ported, since this port has neither the codemode tool nor `tool_search`: such a server is listed in the `mcp_servers` system prompt section with its description, its tools cannot be called, and the interactive mode says so once at startup. An HTTP server that answers 401 fails, because OAuth sign-in is not ported, and `"auth": { "provider" }` is accepted by the config validation but sends no token. The interactive mode reports the servers that failed to connect and the config errors in the transcript at startup; print mode, like upstream's, has no UI to report them in. A connection that drops is not re-established, so that server's tools fail until the next run.

## What matches upstream, and how it is checked

`parity/run.sh` (with `PI_TS` pointing at an upstream checkout with `node_modules` installed, and the models catalog hydrated) runs each check against the TypeScript and against this crate:

- tools (`tools.json`): `read`, `write`, `edit`, `bash`, `grep`, `find` and `ls` on the same files, compared on the exact text, details and error messages they return;
- model resolution (`models.json`): `--model`, `--provider`, `:thinking` suffixes, `--models` scopes and their warnings;
- the system prompt (`prompt.json`): the tools list and rules, context files up the directory tree (with worktree shadowing), SYSTEM.md and APPEND_SYSTEM.md with project trust, `--system-prompt` and `--append-system-prompt`, and skills discovery with frontmatter, ignore files and name collisions;
- print mode end to end (`e2e.json`): `pi -p` and `pi-rs -p` against one scripted OpenAI-compatible server, compared on every request they send (system prompt, tool declarations, messages, tool results) and on stdout, stderr and the exit code.

## Where it differs

- HTTP errors from OpenAI-compatible servers print the whole JSON body (a pi-ai difference, listed in `crates/ai/parity/known.json`), and openai-completions tool declarations carry `strict: false`.
- Skill frontmatter is read by a small YAML reader covering what skills use (plain, quoted and block scalars, booleans); other YAML in a skill file is skipped rather than rejected.
- The docs paths in the system prompt name `$PI_PACKAGE_DIR`, or the directory of the `pi-rs` binary, since there is no npm package.
- `fd` and `rg` are used from the agent's bin directory or `PATH`; they are not downloaded.
- `--mode json` writes no `session` header line, because the header upstream writes describes its JSONL session file and these sessions are SQLite. It also carries pi-durable's own events beside upstream's (`agent_changed`, `submission`, `usage_changed`, `inbox_update`, `deferred_poll`), and fewer `message_update` lines: the harness folds a message's first and last commit into its `message_start` and `message_end`, so `text_start`, `text_end` and a tool call's `toolcall_start` / `toolcall_delta` / `toolcall_end` arrive only when the block lands mid-message, and `tool_execution_update` only for a tool that reports partial output, which no built-in does.
- Assistant messages in that stream carry pi-ai's fields: `durationMs` and `responseId`, no `thinkingLevel`, and a tool call with no `partialArgs` or `streamIndex`; `toolsAdded` carries no `constrainedSampling`, and a tool call's `structuredContent` is the tool's own details object.
- `--list-models` prints the auth each provider has and the catalog pi-ai ships, so its rows for a model match `pi --list-models`'s only while both binaries carry the same catalog: a different `pi` version can list another context window, or a model this crate lacks.
