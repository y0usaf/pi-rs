# pi-coding-agent

Pi's coding agent ([`@earendil-works/pi-coding-agent`](https://github.com/earendil-works/pi)) as the `pi-rs` binary. It runs print mode (`pi-rs -p "..."`), the two headless modes (`--mode json`, `--mode rpc`) and a first port of the interactive mode on [pi-durable](../durable)'s harness and reads the same files as `pi`: settings, `auth.json`, `models.json`, AGENTS.md / CLAUDE.md, SYSTEM.md, APPEND_SYSTEM.md and skills.

Settings are upstream's own layer: the global `<agentDir>/settings.json` and the trusted project's `.pi/settings.json`, deep-merged with the project winning, every schema key with upstream's default, and setters that write back through a lock, replacing only the fields the session changed so keys this port does not know survive. pi-durable's auto-compaction follows them: `compaction.enabled`, `reserveTokens`, `keepRecentTokens` and the per-model overrides, with upstream's 16384 / 20000 when unset.

It won't: show settings screens, or the model and thinking selectors; run any slash command but `/quit`, `/new`, `/name`, `/session`, `/resume`, `/hotkeys`, `/compact`, `/tree`, `/fork`, `/clone`, `/export` and `/import`; answer RPC's `bash`, `abort_bash` and `export_html`, or its extension UI protocol; load themes; run the widgets, child agents and provider streams an extension adds; export a session as HTML.

The flag for what it won't do, `--export`, is refused before anything starts: `pi-rs: --export is not implemented yet`, exit 1. So are upstream's package commands, `install`, `remove`, `uninstall`, `update`, `list` and `config`, as the first argument: `pi-rs: install is not implemented yet`, rather than sent to the model as a prompt; `pi-rs -p install` still sends the word. `--offline`, like a non-empty `PI_OFFLINE`, keeps the model catalog off the network; `--no-mcp` reads no `mcp.json`, `--no-themes` leaves only the built-in themes, `--no-extensions` keeps only the `--extension` paths and `--no-prompt-templates` only the `--prompt-template` paths, as upstream's do. A flag no option or extension defines is `Error: Unknown option: --foo`.

Its behaviour and `pi-ai`'s follow the upstream TypeScript at `bdb1517`; `pi-durable`'s follows `f1b2e77f` ([its README](../durable/README.md) says why the two pins differ). The parity scripts below compare the two on the same inputs.

## Try it

```sh
cargo run -p pi-coding-agent --bin pi-rs -- -p --model anthropic/claude-sonnet-4-5 "list the files here"
echo "summarize this" | cargo run -p pi-coding-agent --bin pi-rs -- @notes.md
```

Without `-p`, on a terminal, it opens the interactive mode (below). `--continue` (`-c`) goes on with the newest session for the working directory; `--session-id NAME` names a new session `NAME.db` and reopens it when it is there; `--no-session` keeps nothing.

`--list-models [search]` prints the models whose provider has auth, as `pi --list-models` does: provider, model, context, max-out, thinking and images, sorted by provider then model id, fuzzy-matched against the search pattern, then exits.

## Interactive mode

`cargo run -p pi-coding-agent --bin pi-rs` (or `pi-rs -c` to go on with the last session) opens a first port of upstream's interactive mode on pi-tui: the editor, the user's messages on their blue background, the assistant's reply streamed as Markdown, thinking in italics, one row per tool call (pending, green or red, with the built-in tools' previews and the bash timer), the working spinner and the two-line footer (cwd and git branch; tokens, cost, context use and model). Keys: Enter sends (while a reply runs it steers), Escape aborts the reply, Ctrl+C clears the editor and twice quits, Ctrl+D quits on an empty editor, Ctrl+O expands tool output, Ctrl+T hides the thinking blocks in the transcript and shows them again, Shift+Tab cycles the thinking level, Ctrl+P and Shift+Ctrl+P cycle through the models in scope, Ctrl+L opens the model selector, Ctrl+G edits the prompt in the external editor (`externalEditor`, else `$VISUAL`, else `$EDITOR`), Ctrl+Z suspends to the background, and the session keys, unbound until `keybindings.json` binds them, start a new session, open the session tree, fork and resume as `/new`, `/tree`, `/fork` and `/resume` do. A line starting `!` runs a bash command in the editor's cwd with the shell `shellPath` and `shellCommandPrefix` name and streams its output into the bordered block upstream draws: the command, the output as the model's copy of it is cut, `(exit N)` or `(cancelled)`, and the truncation warning with the full output's path. Escape kills the command, the editor's border is green while the line starts with `!`, and a `!` line sent while one runs answers upstream's warning. The run is stored as upstream's `bashExecution` message, which the next request carries as `Ran` and the command in backticks with the output fenced; `!!` draws the same block in the dim colour and keeps the run out of that context. A message queued during a reply shows above the status line as `Steering:` (Enter) or `Follow-up:` (Alt+Enter, which waits for the reply to finish), and Alt+Up puts them all back in the editor, as Escape does before it aborts the reply. `<agentDir>/keybindings.json` rebinds them by id, as upstream's does: `{"app.interrupt": "ctrl+k"}`, with the legacy names still read and a value the schema rejects ignored. Typing `/` lists the builtin commands and `@` completes file paths through `fd`. `/quit`, `/new` (a new session file in the same folder), `/name [text]`, `/session`, `/resume` (the session picker), `/hotkeys`, `/compact [instructions]`, `/tree`, `/fork`, `/clone`, `/export <path>.jsonl`, `/import <path.jsonl>`, `/login` and `/logout` work; every other builtin answers that it is not available in pi-rs yet, and an unknown `/x` goes to the model as a message, as upstream does. The screen is built from pi-durable's agent events (`Conversation::events`), so a session killed mid-reply (even `kill -9`) reopens with `-c` showing what was stored, and the harness resumes the unfinished turn. Colors are upstream's `system` theme by default (below), truecolor where upstream's detection picks it (`COLORTERM`, the terminal program, `PI_TRUE_COLOR`).

As upstream's does by default (`tuiMode` `"fullscreen"`), the screen is the terminal's alternate screen: the startup header and the transcript scroll in a view that fills the rows above the pending messages, the status line, the editor and the footer, which keep to the bottom. The `tui.altScreen.*` keys (Page Up and Page Down, half pages, previous and next prompt, top and bottom) and the mouse wheel scroll it, and while it is scrolled away from the end a label above the editor names the key that jumps back. Dragging over the transcript selects text, a double click selects a word, keeping a path or a hyphenated name whole, and a triple click a line; releasing the button copies the selection unless `fullscreenCopyOnSelect` is off, through `wl-copy`, `xclip`, `xsel` or `pbcopy`, or OSC 52 in a remote or headless session, as upstream's `copyToClipboard` picks, and a flash says it was copied or why it was not. Ctrl+Shift+F searches the transcript, Enter and Shift+Enter step through the matches and Escape closes the search. A click on a link opens it in the browser, and the scrollbar can be dragged. The window title is `π - <cwd name>`, or `π - <session name> - <cwd name>` once the session has a name. On exit pi-rs leaves the alternate screen and prints the transcript to the terminal as upstream does with `fullscreenExitOutput` `"transcript"`. `--tui-mode regular`, or the setting, draws inline in the terminal's scrollback instead, and `--verbose` shows the full startup help whatever `quietStartup` says. Ctrl+O expands the startup header into the full key list and the `[Extensions]` listing into each extension's path under its scope. SIGTERM and SIGHUP quit as Ctrl+D does, and the terminal is restored on every way out, a panic included.

Code in fenced blocks is highlighted by a tokenizer of this port's own, not highlight.js: it knows comments, strings, numbers, keywords, function calls and capitalized type names for rust, javascript, typescript, python, bash, go, c, c++, java, kotlin, ruby, lua, sql, css, json, yaml and toml, and colors them with the theme's `syntax*` tokens through upstream's own cli-highlight mapping. A fence in any other language stays `mdCodeBlock`, as upstream draws a language it does not know; where a language is recognized, fewer tokens carry a color than highlight.js gives them.

The startup header follows `quietStartup`: `true` hides it, `"header"` keeps the logo and key hints and drops the details line, and `false` shows both. `treeFilterMode` picks the filter `/tree` opens with.

`/tree` is upstream's session tree (its filter keys, search, folding and branch markers): picking an entry moves the session's leaf there, which pi-durable spells as a forked conversation, and a picked user message reopens in the editor. Two things the tree shows upstream are missing: entry labels (and the label keys and timestamps that go with them) and branch summaries, so picking an entry never asks whether to summarize the branch.

`/fork` lists the session's user messages and `/clone` takes the current leaf; both write a new session file holding the active path up to that point and switch the screen to it, as upstream's branch files do, and `/fork` puts the picked message back in the editor. Each says so in the transcript and names the file it wrote, where upstream says "Forked to new session" or "Cloned to new session" on the status line.

Themes are upstream's own JSON files: `dark` and `light` are built in, and custom themes load from `<agentDir>/themes`, the trusted project's `.pi/themes` and the paths the `themes` setting or `--theme` names, each theme's `vars` and okhsl, oklch, hex or palette-index colors read as upstream reads them. The `theme` setting picks one, and a pair like `light/dark` picks the first theme on a light terminal and the second on a dark one, as `COLORFGBG` reports it. The default, `system`, is generated as upstream generates it from the foreground, background and sixteen palette colors the terminal reports when pi-rs asks at startup: grey until they arrive, palette indices when the terminal answers nothing within 100 ms, and redrawn if the whole answer comes later. The startup header, the loaded resources and the transcript are drawn once that query ends. Unlike upstream, pi-rs does not ask the terminal to report a switch between light and dark (mode 2031), does not ask for the colors again when the theme setting changes, and does not read the `terminal.trueColor` setting. `--use-theme NAME` starts with that theme in place of the setting's. A theme file that does not load says why and falls back to the system theme. In `/settings`, the theme row lists every theme, highlighting one draws the screen with it, and picking one saves it; its `automatic` row picks a theme for each terminal appearance and saves them as the pair.

`/login` configures a provider and `/logout` removes the credential it saved: without an argument `/login` asks whether to sign in with an account or with an API key and then lists the providers, where `/login <provider>` starts the one whose id or name matches. Accounts sign in through upstream's OAuth flows, Anthropic with a loopback callback or a pasted copy-code, GitHub Copilot with GitHub's device code after asking for an enterprise domain, which also stores the account's model ids, OpenAI with a browser callback that returns the client id it registered, OpenAI Codex with a loopback callback or a device code, Kimi For Coding with a device code, Meta with a device code that stores the identity token as `refresh` and mints the Model API key it keeps as `access`, OpenRouter through a loopback callback or a pasted code, which keeps the permanent key it hands out rather than a token to refresh, xAI with a device code, Radius with a browser callback or a device code at the gateway `PI_RADIUS_GATEWAY` names; the dialog shows the URL, the device code and every question the flow asks, Escape cancels, and the credential lands in the same `auth.json` with the same lock and shape as `pi`, so both read it and either refreshes the token. Every provider upstream asks only for a key from takes one here too, `Enter DeepSeek API key` and the rest; Cloudflare AI Gateway, Cloudflare Workers AI and Google Vertex, whose logins also ask for an account, project or location, are not listed and read their environment variables instead. An OAuth endpoint can be pointed elsewhere with `PI_OAUTH_<PROVIDER>_<FIELD>`, as in `PI_OAUTH_ANTHROPIC_TOKEN_URL`, which the login check uses. Every flow polls a device code through one loop with upstream's `device-code.ts` behind it: the five-second default interval, `slow_down` raising it, the expiry deadline and its three messages.

`pi-rs auth` prints a provider's credential or reports whether it is ready, as upstream's `pi auth` does: `print-api-key --provider <id>` and `print-bearer-token [--min-expiry 30m]` write the credential and nothing else, and `check [--json] [--credentials] [--no-refresh]` writes `ready`, `not_ready` or `invalid` and exits 0, 1 or 2, refreshing an OAuth token that expires within five minutes unless `--no-refresh` is given. Every subcommand takes `--provider` or `--model`, and a missing or unknown one is upstream's message and exit 1.

Not there yet: `/share`, `/bug`, `/copy`, `/changelog` and `/reload`, the MCP access Radius's login offers, the model catalog its gateway serves, so a gateway `PI_RADIUS_GATEWAY` names is where the sign-in goes but not where requests do unless `models.json` says so, the login menu's animated Radius row, image display, reloading a theme file as it changes, the 3D logo a click on the header plays, and the startup listing's `[Context]`, `[Skills]` and `[Prompts]` sections and its `[Skill conflicts]`, `[Prompt conflicts]`, `[Extension issues]` and theme diagnostics: only `[Extensions]` is listed, an extension from a package is labelled by its path rather than the package's name, and extension load problems are warnings in the transcript. A `!` command run while a reply streams writes its block into the transcript at once, where upstream keeps it above the editor until the reply ends. A message typed while a compaction runs is sent as a prompt rather than queued for after it. The settings' enable and disable lists for skills and prompts are not read either: a file in the default directories always loads. A resumed session from another folder keeps the current folder, where upstream switches to the session's own; `/resume` reports in the transcript, where upstream uses the status line.

## Codemode

`codemode` lets the model write JavaScript that calls other tools: `--tools +codemode`, or `+codemode` in `defaultTools`. A script is an async function body (`await` and `return` work) in a QuickJS VM inside a hidden child of the `pi-rs` binary, one script per child and at most `PI_CODEMODE_MAX_WORKERS` (2) at a time; the deadline or an abort kills the child, so a `while (true) {}` cannot outlive it and no child is left behind. Scripts see `tools.<name>(args)`, `ALL_TOOLS`, `text()`, `image()`, `console.*`, `exit()`, `store()`/`load()` and `return`, and nothing else: no Node, timers, network or filesystem. A `// @options:` first line sets `max_output_tokens` and `timeout_ms`, and a script with no deadline runs until it ends.

`codemode.mode` decides how the tools are presented, as upstream's `prepareLoadout` does. `on`, the default, keeps the direct tools declared and appends to each one's description how a script calls it ("Codemode: `tools.read(args)` resolves to a string."); the codemode description lists only the tools that are not declared. `only` declares codemode alone, leaves the active direct tools' declarations out of the request as hidden declarations while they stay callable from a script, and lists every one of them in the codemode description under a `### <name>` heading with its TypeScript declaration in a `declare const tools` block, so `defaultTools: ["+codemode"]` with `"mode": "only"` sends exactly one tool. `codemode.inlineBudget` (3000 tokens by default) bounds the declarations: tools that do not fit are left out of the description, cheapest first. A tool's exposure decides where it appears: `direct` (declared, callable while active), `model-only` (codemode itself), `codemode` and `deferred` (callable from a script, never declared, the latter not listed either) and `hidden` (never declared), which is what MCP tools will use.

A nested call runs through the same validation, before/after tool hooks and permission gates as a model-issued one, and reaches the agent's tools without being declared to the model. Only the script's output reaches it: text items are numbered (`==> text 1/2 <==`) when there are several, `console.*` lines follow in one `<console_output>` block, the whole output is truncated to `max_output_tokens` (10000 by default) with the full text spilled to a temp file, and an image from `image()` is saved to a temp file whose path the result names. The result's details carry the nested calls and their durations. A script's `store()` writes become one `codemode-store` entry after its result, and `load()` reads the entries on the current branch from the root, so a value written in an earlier run is still there and `/tree` back to before it brings the older value back.

## Headless modes

`--mode json` is print mode with the session's events as one JSON object per line on stdout instead of the final text, so a client sees the assistant's text as it streams: `pi-rs --mode json -p "list the files here"`. `--mode rpc` takes the same commands upstream's RPC mode does as JSON lines on stdin, and answers them on that one stdout stream beside the events, so a client reads the reply and the stream it caused in order. Every command upstream carries is answered but `export_html` and the extension UI protocol, which say `pi-rs: <command> is not implemented in RPC mode`; a type no mode has says `Unknown command: <type>`. Slash text in a `prompt` is a prompt, since no extension or template here claims the name, as upstream's RPC mode does. A `bash` command runs on its own thread while the loop keeps reading, so its output arrives as `bash_execution_update` lines and `abort_bash` stops it mid-command; the run joins the context as upstream's `bashExecution` message, and the command answers with upstream's `BashResult` (`output`, `exitCode`, `cancelled`, `truncated`, `fullOutputPath`).

`new_session`, `switch_session`, `fork` and `clone` write or open the session file they name and switch the run to it, as the interactive commands do, and `get_tree`, `get_fork_messages`, `get_session_stats`, `get_entries` and `clear_queue` read pi-durable's entries, usage and inbox. `fork` takes the entry ids `get_entries` and `get_fork_messages` report, which are numbers here rather than upstream's short strings, and a branched session replays its entries into a new file, so its ids and its recorded usage differ from the session it came from. `set_steering_mode`, `set_follow_up_mode`, `set_auto_compaction` and `set_auto_retry` are saved to settings and reported by `get_state`, but the run in flight keeps the modes it opened with, which pi-durable fixes while the harness is open.

## Sessions

Each run is one pi-durable conversation in a SQLite file, `<agentDir>/sessions/--<cwd>--/<uuidv7>.db` (or under `--session-dir`, `$PI_CODING_AGENT_SESSION_DIR`, or the `sessionDir` setting). `--session FILE` opens that file, `--session-id NAME` writes to `NAME.db` next to it, `--continue` reopens the newest branch, and `--resume` picks from the sessions in this folder or in all of them. A branch of the tree is another conversation in the same file, forked at the entry the session moved to. `--fork <path|id>` copies a session into a new file under a new id, refusing one whose run is still in flight, and leaves the source untouched. These are not upstream's JSONL session files and `pi` cannot open them; `/export` writes one it can. A session's display name and the session it was forked from are one session-scope document (`pi.session-info`) inside the file, so a copy of the file carries them.

`/export PATH.jsonl` writes the conversation's current branch in upstream's session format (`core/session-export.ts`): the `type: "session"` header, then the branch's entries with `parentId` re-chained, one JSON object per line. `pi --export` reads what it writes. Upstream records each model and thinking change as an entry; pi-durable keeps both in the conversation's agent document, so the file carries the current pair once, at the head, where upstream writes them for a new session. Entry timestamps are the export's, since pi-durable stores no entry times, and a `compaction` entry carries `tokensBefore: 0`. A `pi.reset` entry, which marks where a run's context was reset, has no upstream type and is dropped. A path that ends in anything but `.jsonl`, or no path at all, is upstream's HTML export, which is not ported, so `/export` refuses it. The system-prompt entry carries pi-rs's own prompt, whose codemode tool declares no `constrainedSampling` and whose docs path is pi-rs's, so an export of a session pi-rs wrote differs from `pi`'s only there; a session imported from a `pi` file keeps upstream's prompt and exports identically.

`/import PATH.jsonl` reads an upstream session file into a new `.db` in the session directory, named after the file's session id, with the token totals its messages carry and the file's model, thinking level and cwd set on the conversation. It asks `Import session` / `Replace current session with <path>?` first, as upstream's confirm dialog does, and `Import cancelled` when the answer is no. The loop then switches to that file, as upstream's import does: the session's model, thinking level and cwd become the file's, and the chat redraws from its transcript, so `/session` reports it without a restart. A file whose cwd no longer exists is refused, naming both paths as upstream does, though upstream then offers to use the current directory and this does not. Entry types with no durable place are dropped — `label`, `custom`, `custom_message`, `branch_summary`, `usage` and `session_info` (the session's name) — a `model_change` or `thinking_level_change` becomes the conversation's model or thinking level instead of an entry, and a `context_edit` whose target is in the file is kept. The JSONL files `pi` keeps are then readable here, and a session this writes back out is the file upstream wrote, apart from ids and timestamps.

## MCP servers

Servers come from `<agentDir>/mcp.json` and, in a trusted project, from `<cwd>/.pi/mcp.json`, both in the `mcpServers` shape other MCP clients use: a `command` starts a stdio server, a `url` reaches a streamable HTTP one, and a project entry replaces a global one of the same name, or overrides its `enabled`, `exposure` and `toolExposure` when it sets nothing else. They connect before the first turn, which waits at most ten seconds for them, and their tools are the agent's own, named `mcp__<server>__<tool>` (with a `sha256` suffix when a name is too long or two tools sanitize to one name): the server's `inputSchema` becomes the tool's parameters, and a result's content blocks become text and images, with text over 20KB cut in the middle and the whole output in a temp file. `--no-mcp` reads no `mcp.json` at all.

A server's tools are declared to the model only with `"exposure": "direct"`, or a `toolExposure` entry that says so. The default, `codemode`, and `deferred` are not ported: only a server's direct tools are registered, so neither the codemode tool nor `tool_search` can reach the others, and neither is activated for them as upstream's mcp extension does; such a server is listed in the `mcp_servers` system prompt section with its description, its tools cannot be called, and the interactive mode says so once at startup, even when codemode or `tool_search` is active. An HTTP server that answers 401 fails, because OAuth sign-in is not ported, and `"auth": { "provider" }` is accepted by the config validation but sends no token. The interactive mode reports the servers that failed to connect and the config errors in the transcript at startup; print mode, like upstream's, has no UI to report them in. A connection that drops is not re-established, so that server's tools fail until the next run.

## Extensions

`packages` (a package directory, a store path for an npm package), the `extensions` setting, `--extension` and the `<cwd>/.pi/extensions` and `<agentDir>/extensions` directories name what to load, and the child finds inside them what upstream's resource loader finds: one level deep, by `package.json`'s `pi.extensions`, `index.ts` or `index.js`. One Node child per session imports each entry point with Node's own type stripping and calls the factory, and gives an extension's own ES modules the `__filename`, `__dirname` and `require` that upstream's jiti gives every module; it comes from the `extension-host` directory installed beside the binary, and `PI_EXTENSION_HOST` names another copy.

A command a factory registers is listed where upstream lists it — `/` autocomplete and RPC `get_commands`, as `"source": "extension"` with the entry point's path; upstream tags the autocomplete entry with where the extension came from (`[u]` for the agent directory) and pi-rs does not. Typing one runs the command's handler with the text after its name, in place of sending the prompt, as upstream does. The child answers `@earendil-works/pi-coding-agent`, `@earendil-works/pi-ai` and `@earendil-works/pi-tui` with a stub, so a package that imports from them loads: `getAgentDir()` answers with the agent directory, `defineTool` returns its tool, pi-ai's `Type` is typebox's, and every other member records itself the first time a package uses it, which the session then reports as `Warning: <path> uses registerShortcut, which pi-rs does not implement yet`.

A tool an extension registers, while loading or later from a handler, is the model's as upstream's would be: `direct` and `model-only` tools are declared unless `defaultActive` is false, `codemode` and `deferred` ones are reached only through codemode, which lists them all, and a tool named like a built-in replaces it. Its `execute` runs in the child with the call id, the arguments, an `AbortSignal` that Escape and RPC `abort` fire, `onUpdate` and a context; partial results arrive as `tool_execution_update`, and the result, a thrown error or `terminate` come back as upstream's. Requests to the child run side by side, so a tool that takes minutes holds up no event, command or other tool, and what an extension calls (`notify`, `sendUserMessage`) takes effect when it is called rather than when its handler returns.

Tool calls reach extensions as upstream's agent loop runs them. Once the reply is stored, each of its calls gets `tool_execution_start` and then its `tool_call` handlers, in the reply's order, before any call runs, or, in a round run one call at a time (a tool with `executionMode: "sequential"`), just before that call runs: a handler that returns `block` settles the call with its `reason` (else `Tool execution was blocked`) and `terminate`, one that throws settles it with the error's message, and one that changes `event.input` in place changes what the tool runs with. A call to a tool the model was not offered, or with arguments that fail validation, gets its start and end at once and no `tool_call`. An extension tool's `onUpdate` reaches `tool_execution_update` handlers while it is called, with the partial result as given, and the tool's result waits for them, as upstream's does; another tool's progress arrives at the harness's output pace; when it returns, `tool_result` handlers may replace its `content`, `details`, `isError` and `usage`, and `tool_execution_end` carries the result the model sees, with `terminate` when the call asks the run to stop after its round and `durationMs` when the tool ran. The round's results then get `message_start` and `message_end` in the reply's order, or, in a round run one call at a time, each right after its call's end. A call a tool makes, as a codemode script's `tools.<name>()` does, has the id `<calling id>/<n>`, and its `tool_execution_start`, `tool_call`, `tool_result` and `tool_execution_end` carry `parentToolCallId`, in upstream's order. While a round runs, `ctx.sessionManager` holds none of its results that upstream would not have stored yet. Not yet: tool results are stored as they finish, so `turn_end`'s `toolResults`, `context` and `ctx.sessionManager` list a round's results in finishing order where upstream's follow the reply; the built-in tools return no `structuredContent` and report no partial output, so `read` and `bash` lack upstream's `structuredContent` in `tool_result` and `tool_execution_end`, and `bash` sends none of upstream's updates; a call a tool makes reports its progress as its caller's `tool_execution_update`, `--mode json` writes none of its events, and the caller's result message carries no `nestedCalls` record of it.

A package that fails to load is reported as upstream reports it, `Warning: Failed to load extension: <message>`, and the session goes on; with nothing configured no child starts and nothing changes.

The events upstream hands extensions reach them through the harness. `session_start`, `session_shutdown` (reason `quit` only), `agent_start`, `agent_end` with every message the run handed `message_end`, in that order and as its handlers left it, `agent_settled` once the queue is empty, `message_start` as a reply's stream starts, with its empty partial, `message_update` for every stream event with upstream's `assistantMessageEvent` and the message as the provider has built it from everything received so far, as upstream's handlers see its live message, `message_end`, `input` before a prompt is sent, `before_agent_start` before a prompt starts a run, `turn_start` before a turn's first request, and `turn_end` once the turn's reply and tool results are stored, with upstream's boundary fields (`messageEntryId`, `toolResultEntryIds`, `outcome`, `entries`, `continue` and a `context` built from the session the child holds). `before_agent_start` hands upstream's `systemPromptOptions`, rendered as `systemPrompt` and `ctx.getSystemPrompt()` by upstream's own code: what its handlers leave there is the run's system prompt, and a `systemPrompt` they return replaces the system messages of the run's requests, as upstream's forced prompt does, without being stored. A message it returns is stored after the prompt as upstream's `custom_message`, a `pi.custom-message` entry whose message is the user message `convertToLlm` makes of it, so the run's first request and every later one carry it, and goes through `message_start` and `message_end` after the prompt; the TUI draws it as upstream does, the `[customType]` label over its text on the custom-message background, when `display` is true, and `/export` writes it as `custom_message`. A message queued while a run streams (`steer`, `follow_up`, Enter in the TUI) runs as more turns of that run, as upstream's agent loop does: no second `before_agent_start` or `agent_start`, a `turn_start` and `turn_end` for each turn, the run's system prompt until the run is over, and a steer and a follow-up queued together taking a turn each, the steer first. `turn_end` goes out once the turn's reply and tool results are stored and before a queued message is placed, to handlers registered at any time, with `context.pendingMessages` holding the message the next turn takes; the `entries` its handlers return are stored before that message (`custom` as a `pi.custom` entry, `custom_message` as above, `context_edit` and `compaction` as pi-durable's own), and `continue` runs one more turn on the context when nothing is queued and the context can go on, as upstream checks. A turn that ends in an error or an abort gets its `turn_end` once the run is over or the next request starts, and a run that then goes on (a retry, or queued messages) ends with `agent_end` and starts again with `agent_start`, keeping the run's system prompt, as upstream's does. Each `agent_end` carries the messages handed `message_end` since its `agent_start`; the `turn_end` entries are stored without either. Not yet: `toolSnippets` and `toolGuidelines` lack upstream's `powershell` and `tool_search`, which pi-rs does not have, and skills carry no `sourceInfo`. An answer changes what is stored: a `message_end` handler that returns a message of the same role replaces the message before it is committed — on the abort path too — so a resumed session reads the replacement, and an `input` handler's `transform` is what the model sees. `ctx.abort()` stops the run the way Escape does, `ctx.ui.notify` shows a notice, `pi.exec(command, args, options)` runs a program without a shell in the session's directory (or `options.cwd`) and answers upstream's `{ stdout, stderr, code, killed }`, killing its whole process group on `options.timeout` or `options.signal` (SIGTERM, then SIGKILL five seconds on, where upstream signals only the program and its SIGKILL never follows); a program still running when the child closes — pi-rs quits, is killed, or gives up on a wedged handler — is killed with it, a job it left in the background (`cmd &`) included, where upstream's outlives pi. The child tells pi-rs each process group it starts, so pi-rs kills them itself when the child is stuck in synchronous code and has to be killed; only killing pi-rs while the child is stuck leaves both running. And `sendUserMessage` with `deliverAs: "followUp"` queues a turn after this one. `ctx.sessionManager` answers `ReadonlySessionManager`'s getters (`getEntries`, `getBranch`, `getEntry`, `getLeafId`, `getLeafEntry`, `getHeader`, `getTree`, `getSessionFile`, `getSessionId`, `getSessionDir`, `getSessionName`, `getCwd`) with the entries `/export` writes, sent to the child again whenever an entry is stored, and `pi.getActiveTools()` and `pi.getAllTools()` list the session's tools and the extensions' own. As upstream's, those two and `sendUserMessage` throw while a factory runs.

The catalog grows as upstream's does. Each built-in provider but Radius takes the models pi.dev's catalog adds or changes from `<agentDir>/models-store.json`, the file upstream pi writes, as pi-rs starts. Interactive mode then asks `https://pi.dev/api/models/providers/<id>` (or `PI_CATALOG_URL`'s host), in the background with fifteen seconds to answer, for each provider that has credentials and was last asked over four hours ago, sending the stored `etag` so an unchanged catalog answers 304, and writes what comes back to the same file. `ctx.modelRegistry.refresh({ allowNetwork, force, providers })` runs the same refresh for an extension, `force` asking even inside the four hours, and answers upstream's `{ aborted, errors }`, a `Map` from provider to `Error`; the models it finds are in `getAll()` and `find` at once, and a request can go to them. Not yet: RPC mode does not refresh in the background as upstream's does.

Providers come from both sides. `builtinProviders()` from `@earendil-works/pi-ai/providers/all` lists the built-in catalog's providers, with the OAuth login's `id` and `name` as `auth.oauth` where the provider has one, and each provider's `streamSimple` asks pi-rs to run the request with its own client for the model's API and the options it is given (`apiKey`, `headers`, `maxTokens`, …), handing every event back as it comes; aborting `options.signal` cancels the request. `pi.registerProvider(provider)`, or `(id, config)`, makes requests to that provider's models go to its `streamSimple` in the child, with the credentials pi-rs resolved in `options.apiKey`, and `unregisterProvider` hands them back. A registered provider whose `auth.oauth.id` names a built-in OAuth provider is a second login for it, such as `anthropic#2`: its token in `auth.json` is refreshed with that provider's flow, `ctx.modelRegistry.getProviderAuthStatus(id).configured` says whether one is stored, and `getProviderAuth(id)` answers `{ auth: { apiKey, headers, baseUrl }, env }` for it, or nothing. `ctx.modelRegistry` reads the models pi-rs last sent when it is called, not when the handler started, and `createAssistantMessageEventStream` is upstream's event stream. Not yet: `/login` does not offer the logins extensions register (upstream pi's `/login` writes the same `auth.json`), the models a provider registers are not added to the catalog, and the built-in stream ignores `options.fetch`, `onPayload`, `onResponse` and `env`, so a wrapper never sees a response's headers, a 429's `retry-after` included.

Requests reach extensions as upstream's do. Each request the agent loop sends, through any built-in API or an extension provider's `streamSimple`, fires `before_provider_request` with the body as upstream's builder makes it, unset keys included, and sends what the handlers return; `after_provider_response` follows with the status and headers wherever upstream's API reports a response, which Google's and Vertex's do not, and `provider_stream_event` carries each event the provider streams, parsed, before pi-rs reads it. Summaries and `ctx.modelRegistry.complete` fire none of these, as upstream's don't. `pi.registerVirtualModel` adds the model to the catalog, so `--model <provider>/<id>` selects it, and its `route` picks each request's model with upstream's `reason` (`user`, `continuation`, `retry`, `direct`), `previous`, `failed` and the state it last returned, kept on the session as a `pi.virtual-model-state` custom entry; the model it picks must be a physical one with credentials, and the request is checked against that model's context window, compacting first when it is over the threshold, and then sent to it without asking `route` again. `ctx.getContextUsage()` estimates the context with upstream's code over the session the child holds, and `ctx.compact()` aborts the run, compacts, and calls `onComplete` with the result or `onError`. Not yet: `before_provider_headers`; Google's, Mistral's and Bedrock's bodies and stream events are their wire shape, not the SDK objects upstream hands handlers, and Codex's WebSocket reports `response.done` as the `response.completed` pi-rs maps it to; and pi-ai retries a failed HTTP request itself, twice by default where upstream does not and without reading `retry.provider`, so only a failure that outlasts those retries reaches `route` as `retry`.

An event or command handler may go ten seconds without a word from the child, not counting time the child spends waiting on pi-rs (a `complete`), before the child is taken for wedged and the event dropped, so an extension that hangs cannot hang the TUI; a tool has no limit and stops only when cancelled. A tool's `onUpdate` text shows only while each update extends the last, since a tool's output here only grows; `prepareArguments`, `renderCall`, `renderResult`, `promptSnippet` and `promptGuidelines` are not used yet, and a `direct` tool with `defaultActive: false` stays callable from codemode. Two shapes differ from upstream: `message_end` answers only for assistant messages and `input` only for a prompt that is one text block. `ctx.sessionManager` holds the current branch only, so `getEntries` is `getBranch` and `getTree` one chain; its entries carry the time they were read, `getLabel` answers nothing, and `buildContextEntries` and `buildSessionProjection` are missing. Print mode sends it between runs and before each `turn_end`, so a handler inside a turn sees the session as the turn found it.

## Embedding

`pi_coding_agent::cli::main()` is the whole `pi-rs` binary. A program that calls `mount::set` before it adds models and pi-durable extensions written in Rust to every harness the run opens: the mount's catalog resolves with `--model` and lists as available without credentials, and its `open` gets the built-in providers and returns the models every request goes through, so it can answer for its own models and pass the rest on. `nix flake check`'s `mount-e2e` mounts a fake model and a tool and checks that a print-mode turn calls the tool through the mounted model, that a run the tool ends prints the reply before it and a continued session's wordless run prints nothing, that `--list-models` lists the model, and that plain `pi-rs` does not know it.

## What matches upstream, and how it is checked

`parity/run.sh` (with `PI_TS` pointing at an upstream checkout with `node_modules` installed, and the models catalog hydrated) runs each check against the TypeScript and against this crate:

- tools (`tools.json`): `read`, `write`, `edit`, `bash`, `grep`, `find` and `ls` on the same files, compared on the exact text, details and error messages they return;
- model resolution (`models.json`): `--model`, `--provider`, `:thinking` suffixes, `--models` scopes and their warnings;
- the system prompt (`prompt.json`): the tools list and rules, context files up the directory tree (with worktree shadowing), SYSTEM.md and APPEND_SYSTEM.md with project trust, `--system-prompt` and `--append-system-prompt`, and skills discovery with frontmatter, ignore files and name collisions;
- print mode end to end (`e2e.json`): `pi -p` and `pi-rs -p` against one scripted OpenAI-compatible server, compared on every request they send (system prompt, tool declarations, messages, tool results) and on stdout, stderr and the exit code;
- the modes end to end (`examples/modes_e2e.rs`, run by `nix flake check`): the `--mode json` events of a run, a prompt template from the agent directory expanding in a print-mode prompt, and `--mode rpc` answering commands and switching, forking and cloning a session;
- the codemode sandbox (`checks.codemode-e2e`): the hidden child's messages, a script calling a tool, the typo guard, a script waiting on nothing, the deadline, an abort, the memory limit, `store()` writes and a value stored in one run and loaded in the next, `@options` parsing, and a `pi-rs -p` run whose model calls `codemode` with a script that calls `read`.

`nix flake check`'s `extensions-e2e` writes an extension of its own and drives the built binary with it: `packages` names it, a command appears in RPC `get_commands` with the schema the package computed at load, `--extension` adds a second, `--no-extensions` keeps only that one, a package that throws and one that uses a member pi-rs lacks are reported and leave nothing behind, and an empty settings file starts no child. In a print-mode run against a fake model it checks that every event arrives, that a `message_end` replacement is what the next request holds in place of the reply, that an `input` transform is what the model was asked, that a command runs with its arguments, that `ctx.sessionManager.getBranch()` holds the stored replacement after each turn, that `getActiveTools` names the session's tools, and that the extension's module has `__dirname`, `__filename` and `require`. A `pi.exec` whose program tree ignores SIGTERM and keeps writing returns killed between SIGTERM and SIGKILL, and a program still running, or left in the background by a call that returned, leaves no process once pi-rs quits after an abort, is killed, or gives up on an `input` handler that waits on it or spins. In a `--mode json` run, a tool registered while loading and one registered at `session_start` are both offered to the model, and the later one runs in the child with its progress as `tool_execution_update` and its result in the next request; in RPC mode, an `abort` while an extension tool waits reaches the tool's signal. Against a fake Anthropic endpoint that answers the stored key with a 429, an extension that registers `anthropic#2` and an `anthropic` whose `streamSimple` retries a failed request on the next login gets the second login's OAuth token from `getProviderAuth` and prints the endpoint's answer to it, streamed through the built-in client and the extension.

`nix flake check`'s `extensions-parity` runs every entry of upstream v1.4.0's `examples/extensions` (each `.ts` file and each directory's `index.ts`, with the npm dependencies its `package-lock.json` pins) through the pinned upstream `pi` and the built `pi-rs` in `--mode json` against one scripted server, and prints how many cases are the same and how many handlers in how many cases `unexercised.json` exempted. An entry runs the scenario `parity/extensions/<entry>.json`, or one case per `<entry>.<case>.json`, or else the prompt `hi` answered with `done`; a scenario holds the prompts, sent in order as `pi -p` takes several, or instead RPC commands, sent one at a time to `--mode rpc`, each awaited for its response and a prompt's run for `agent_settled`, with every dialog an extension opens answered as cancelled, extra command-line arguments, the model's scripted turns with the usage each reports and, as `after`, a callback whose run the turn waits for before it is answered, providers whose models the scripted server answers too, and files to seed under the cwd and the agent directory. Each entry is loaded through `parity/extensions/probe.ts`, which logs at the extension boundary every call it makes on `pi` and `ctx`, every property it reads, every handler and callback the host calls, including those nested in plain objects and arrays, each with its arguments and what it returned or threw; class instances it hands over, such as components, pass through unwrapped, so the host's calls on them are not logged. A `setInterval` the entry starts is logged as a callback named by its delay on each tick, and only its first tick and the calls that tick makes are compared, in place, since how often it fires is wall time. From that log each side's run lists the handlers the entry registered on `pi` (event handlers, a tool's `execute` and other callbacks by tool name, command handlers, provider and event-bus callbacks, and flags, which count as run and returned once read), which of them the host called, and which returned at least once. Coverage is judged across all scenarios of an entry: a case fails when no scenario has upstream call a handler the entry registered, or have one call of it return, unless `parity/extensions/unexercised.json` names it with the reason, either as a handler no print-mode or RPC input reaches or, marked `ran`, as one that runs but cannot finish its work in the check. A case also fails when upstream calls a handler that file says cannot run or never calls one it marks `ran`, and a run of every case fails when a pattern in that file matches nothing. It also fails when upstream does not load the entry, either side exits nonzero, a side's request count differs from the scripted turns or a scripted tool call did not run as scripted, or when the two sides differ in the extension-visible events (`agent_start`, `turn_start`, `message_end`, `tool_execution_*`, `turn_end`, `agent_end`, and in RPC the responses, extension UI requests and extension errors), the probe log, stderr or the files left in the cwd, once message timestamps, execution durations, bash's `wall_time_seconds`, entry, session and UI request ids, scratch and docs paths are normalized. An extension tool's `tool_execution_update` is compared without its `details`, since upstream may write it after the tool changed that object; instead, on each side, each field of every such update must equal that field as the tool passed it to `onUpdate` at that call or a later one. Arguments name cases to run only those. The other `--mode json` differences listed below are not compared here.

`nix flake check`'s `tui-parity` drives the pinned upstream `pi` and the built `pi-rs` in interactive mode, each in its own pseudo-terminal of 30 rows by 100 columns with the same environment, a fresh home, agent directory and cwd at one path, and a scripted model, through the cases in `examples/tui_parity.rs`: startup and a prompt, and one case each for `ctx.ui.notify`, a select and a confirm answered and a select cancelled, `ctx.ui.setStatus` across a turn, `ctx.ui.setWidget` across a resize, a `ctx.ui.custom` overlay, `pi.registerShortcut` and `pi.registerMessageRenderer`, each with one upstream example extension. What a side writes goes through the `vt100` terminal emulator, which answers device-attributes and cursor-position queries as a terminal without the Kitty keyboard protocol would. A case types keys, resizes, and at each checkpoint waits until the screen shows (or no longer shows) the text the checkpoint names and nothing has been drawn for a second, then compares the visible cells with their colors and attributes (on a blank cell only the background, underline and inverse, and the foreground color when underline or inverse shows it), the cursor's position and visibility, the alternate screen and the window title. Each case prints `same` or `DIFFERS` with, per checkpoint, the differing rows not shown at an earlier one, then `tui parity: N of M cases same`; a side that does not reach a checkpoint within 30 seconds stops there. `tui-parity-baseline` runs upstream against itself. `PI_TUI_PARITY_KEEP=<dir>` keeps every checkpoint's screen and each side's raw terminal output; arguments name cases to run only those.

`nix flake check`'s `extensions-queue-parity` runs one extension, `parity/queue/extension.ts`, through the pinned upstream `pi` and the built `pi-rs` in three scenarios against one scripted server and prints how many are the same: in `--mode rpc`, a prompt whose first request the server holds while a `steer` and a `follow_up` are queued, and the prompt `continue`, whose first `turn_end` returns a custom entry and a custom message and asks the run to continue; and in the TUI on a pseudo-terminal, once the extension has loaded, the terminal is raw and the footer names the model, a prompt whose first request is held while a second line is typed and queued as a steer. At `before_agent_start` the extension adds a message and a marker to the system prompt, and it handles `agent_start`, `turn_start`, `agent_end` and `agent_settled` without acting; it is loaded through `parity/extensions/probe.ts` as in `extensions-parity`. A scenario fails when upstream does not load the extension, either side exits nonzero, a side's request count differs from the scripted replies, or the two sides differ in the probe log, normalized as in `extensions-parity`, or in the messages each request carries, each as its role and text with the system prompt reduced to whether it holds the marker; the screen is not compared. A side is done once it has used every scripted reply and its extension has seen `agent_settled` since the last request, or has gone three seconds without a request or a probe record, and in RPC mode `get_state` also reports it idle with nothing queued. `extensions-queue-parity-baseline` runs upstream against itself. Arguments name scenarios to run only those.

`nix flake check`'s `auth-e2e` drives `pi-rs auth` on the built binary against a fake token server: the credential `print-api-key` and `print-bearer-token` write, `check`'s status, its `--json` and `--credentials` shapes and its 0, 1 and 2, the refresh a token inside `--min-expiry` gets and the `auth.json` it is written back to, and the errors an unknown provider, an OAuth credential asked for as an API key and an unknown flag get.

## Where it differs

- A print-mode run that a tool ends (an extension tool whose result terminates the run, as fusion's `finish` does) prints the last assistant text that run produced before that result, never an earlier run's reply in a continued session; upstream prints nothing, since the run's last message is the tool's result.
- HTTP errors from OpenAI-compatible servers print the whole JSON body (a pi-ai difference, listed in `crates/ai/parity/known.json`), and openai-completions tool declarations carry `strict: false`.
- A `// @options:` line holding invalid JSON reports the JSON parser's own message, which reads differently from V8's.
- A script's nested calls run one at a time, where upstream runs a script's concurrent calls in parallel, because pi-durable's harness is synchronous: a tool call cannot run beside another.
- The codemode tool's description lists no `searchTools`, `describeTool`, `describeNamespace` or `models` namespace, which are not ported, and the prelude's typo hint still mentions `searchTools`.
- A codemode row shows its nested calls when the script ends, not as they run. A codemode call a crash interrupts is reported as `Tool codemode was interrupted and may have partially run`, where upstream replays the script and hands it the nested results it already had: pi-rs keeps no nested-call journal, so a replay would run those tools a second time.
- `/tree` lists a `codemode-store` entry as `[codemode-store]`, where upstream's generic custom-entry row reads `[custom: codemode-store]`.
- A nested call resolves to the tool's text: no pi-rs tool declares structured output, so `tools.bash(...)` resolves to a string where upstream's resolves to an object with `exit_code`, `output` and the rest, and the description says `Promise<string>`.
- The codemode description groups tools by namespace upstream; pi-rs has no namespaces yet, so every tool is listed under one `Nested tools:` heading.
- Skill frontmatter is read by a small YAML reader covering what skills use (plain, quoted and block scalars, booleans); other YAML in a skill file is skipped rather than rejected.
- The docs paths in the system prompt name `$PI_PACKAGE_DIR`, or the directory of the `pi-rs` binary, since there is no npm package.
- `fd` and `rg` are used from the agent's bin directory or `PATH`; they are not downloaded.
- `--mode json` writes no `session` header line, because the header upstream writes describes its JSONL session file and these sessions are SQLite. It also carries pi-durable's own events beside upstream's (`agent_changed`, `submission`, `usage_changed`, `inbox_update`, `deferred_poll`), and fewer `message_update` lines: the harness folds a message's first and last commit into its `message_start` and `message_end`, so `text_start`, `text_end` and a tool call's `toolcall_start` / `toolcall_delta` / `toolcall_end` arrive only when the block lands mid-message, and `tool_execution_update` only for a tool that reports partial output, which no built-in does and an extension tool's `onUpdate` does.
- That stream writes a round's tool result messages as each is stored, where upstream writes them after the round's last `tool_execution_end`, in the reply's order, when its calls run side by side; in a round run one call at a time it writes a call to a tool the model was not offered ahead of the calls before it; its `tool_execution_update` carries no `args` and pi-durable's form of `partialResult`, and its `tool_execution_end` no `terminate`.
- Assistant messages in that stream carry pi-ai's fields: `durationMs` and `responseId`, no `thinkingLevel`, and a tool call with no `partialArgs` or `streamIndex`, and codemode's declaration in `toolsAdded` carries no `constrainedSampling`.
- `--list-models` prints the auth each provider has and the catalog pi-ai ships with what `models-store.json` holds over it, so its rows for a model match `pi --list-models`'s once either binary has refreshed that file: before then a different `pi` version can list another context window, or a model this crate lacks.
